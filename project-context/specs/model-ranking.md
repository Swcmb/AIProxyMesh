## 一、综合排名公式

针对每个模型计算 0–100 分的综合得分。Zen 与 Go 是同一模型的接入路线，排名阶段合并：费用取最便宜路线，可用性与能力取最好值，成功率与 P95 延迟按渠道汇总。

$ \boxed{ S(r,t)=G(r,t)\times \left[ 0.40Q(r,t)+0.20E(r,t)+0.25A(r,t)+0.15F(r,t) \right] } $

推荐初始权重：以 OpenCode Agent 编程任务为主要使用场景。所有分项均归一化为 0–100 分。

| 符号 | 评价维度         | 权重   | 主要目的                                         |
| ---- | ---------------- | ------ | ------------------------------------------------ |
| $Q$  | 大模型能力       | 40%    | 判断模型解决任务的能力                           |
| $E$  | 费用经济性       | 20%    | 判断完成同等任务的成本                           |
| $A$  | 可用性           | 25%    | 判断稳定性、响应速度和额度余量                   |
| $F$  | 任务与能力适配度 | 15%    | 判断文本、多模态、上下文、工具调用等是否适合任务 |
| $G$  | 准入条件         | 0 或 1 | 检查必要能力和接口是否满足要求                   |

其中，$r$ 表示具体接入路线，$t$ 表示任务类型。

例如，`GPT 6 Luna + Zen` 和 `GPT 6 Luna + Go` 应当是两条独立的排名记录。即使基础模型相同，它们的价格、额度、延迟和实际成功率也可能不同。

## 二、四项评分具体怎么算

### 1. 大模型能力分 Q：40%

不要直接把不同网站的原始分数相加。建议将各项测评转换成候选模型中的百分位排名，再加权计算。

$ Q=0.50L+0.30B+0.20I $

| 指标              | 占 Q 的比例 | 说明                                   |
| ----------------- | ----------- | -------------------------------------- |
| $L$：排行榜表现   | 50%         | LMArena 对应任务分类的百分位           |
| $B$：专项基准成绩 | 30%         | 编程、推理、视觉等领域基准测试的百分位 |
| $I$：内部实测成绩 | 20%         | 在统一测试任务集上的实际通过率         |

不同任务需要采用不同的专项基准：

- 编程： 代码生成、修复缺陷、仓库级任务、Agent 工具调用。
- 推理： 数学、逻辑、复杂问题分析。
- 文本： 指令遵循、知识问答、长文本理解。
- 视觉与多模态： 图像理解、图表分析，以及实际所需的音视频能力。

对于缺少部分基准数据的新模型，按照其余可用指标的权重重新归一化，不应直接按零分处理。

这里的百分位是相对于同一批候选模型计算的。它可以降低不同排行榜量纲不同带来的影响。

### 2. 费用经济性 E：20%

真正应该比较的是：完成同一种任务，平均花费多少钱。

首先定义标准任务的成本 $C_r$。

对于 Zen，按照实际计费价格估算：

$ C\_{\text{Zen}}= \frac{ T_iP_i+T_oP_o+T_cP_c }{10^6} $

其中：

- $T_i,T_o,T_c$：输入、输出和缓存读取 Token 数量。
- $P_i,P_o,P_c$：对应的每百万 Token 价格。

需要支持缓存写入收费时，再增加对应的 Token 项。

对于 Go，建议同时记录两个成本口径：

| 成本指标   | 核算方式                         |
| ------ | ---------------------------- |
| 实际现金成本 | 将每月订阅费分摊到预计月度成功任务数           |
| 额度消耗成本 | 根据标准任务的 Token 用量和模型对应的额度消耗估算 |

例如 Go 订阅费为每月 10 美元，预计每月完成 1,000 个任务，那么分摊后的平均订阅成本为每个任务 0.01 美元。额度不足、限流和耗尽风险另外进入可用性评分。

这样既保留真实现金成本，也能体现重型模型消耗额度更快的事实。Go 的不同模型确实存在不同的使用额度，且订阅本身有使用窗口限制。

统一得到每条路线的单任务有效成本 $C_r$ 后，使用以下公式归一化：

$ \boxed{E(r,t)=\frac{100}{1+C_r/C\_{\mathrm{ref}}}} $

其中 $C\_{\mathrm{ref}}$ 是同一任务下所有符合准入条件的候选路线的中位单任务成本。

这个公式的特点是：免费任务的经济性得分为 100；成本越高，得分越低；成本翻倍时得分仍然连续变化，不会因超出某个价格上限而失去区分度。

### 3. 可用性 A：25%

可用性应该依赖真实运行数据，而不是单纯依据服务商的宣传。

$ \boxed{A=0.60U+0.25L_a+0.15H} $

| 指标            | 权重 | 计算方式                                         |
| --------------- | ---- | ------------------------------------------------ |
| $U$：成功率     | 60%  | 成功返回有效结果的请求数 ÷ 总请求数              |
| $L_a$：延迟得分 | 25%  | 根据 P95 响应延迟归一化                          |
| $H$：额度余量   | 15%  | 根据计费余额、限流额度及各使用窗口的剩余额度计算 |

延迟得分可以采用线性截断函数：

$ L_a=100\times \operatorname{clip} \left( \frac{D\_{\mathrm{bad}}-D\_{95}} {D\_{\mathrm{bad}}-D\_{\mathrm{good}}}, 0,1 \right) $

$D\_{95}$ 是 P95 延迟，$D\_{\mathrm{good}}$ 和 $D\_{\mathrm{bad}}$ 是运维配置的 ideal 与不可接受延迟（`ranking.latency_good_ms` / `ranking.latency_bad_ms`）。

建议使用最近 7 天的数据作为主窗口，同时保留最近 24 小时的短期状态。对 Go 检查短时、周度及月度额度；对 Zen 检查余额和限流状态。

可用性至少区分以下失败类型：`401`、`429`、`5xx`、超时、连接失败、空响应、无效响应。这样才能进一步判断究竟是 Key、模型服务、代理连接还是额度问题。

### 4. 任务适配度 F：15%

多模态是模型的能力属性，不是所有任务都应该加分的优势。

建议：

$ F=0.50M+0.25C_x+0.25T_o $

| 指标              | 说明                                                   |
| ----------------- | ------------------------------------------------------ |
| $M$：模态适配     | 是否支持当前任务要求的文本、图像、音频或视频输入输出   |
| $C_x$：上下文适配 | 上下文长度、最大输出长度能否满足任务                   |
| $T_o$：Agent 适配 | Tool Calling、结构化输出、流式输出等所需功能的适配程度 |

关键设计是：硬性要求必须通过准入检查，软性能力再参与评分。

例如，当前任务要求输入图片，而某模型不支持视觉输入，那么：

$ G(r,t)=0 $

该路线不参与本次任务排名。一个纯文本模型不应该因为价格极低、速度极快而被排到视觉任务榜首。

对于 OpenCode Agent，还应特别检查 Tool Calling 和上下文能力。纯聊天效果优秀，不一定代表它能稳定地执行多步编程任务。

## 三、不同任务使用不同权重

同一模型在文本、编程与视觉任务中的综合表现可以差异很大。因此，默认采用以下三套预设权重。

| 场景           | 大模型能力 Q | 费用 E | 可用性 A | 任务适配 F |
| ------------ | ------- | ---- | ----- | ------ |
| Agent 编程（默认） | 40%     | 20%  | 25%   | 15%    |
| 通用文本问答       | 35%     | 25%  | 25%   | 15%    |
| 视觉及多模态任务     | 35%     | 15%  | 25%   | 25%    |

在编程任务中，模型的代码能力与执行工具的可靠性优先；在多模态任务中，支持相应输入输出能力的重要性提高；在日常文本任务中，适度提高费用权重。

实际系统可以根据调用记录中的任务分布继续调整权重。

## 四、Zen 和 Go 应该如何统一排名

模型能力层

同一基础模型的专项基准、排行榜成绩和内部实测结果可以共用，但必须记录数据来源、版本和时间。

接入路线层

Zen 和 Go 分开记录价格、额度、延迟、请求成功率、接口兼容性和实际执行效果；这一层只服务采集与 Go 轮转，不对外暴露为排名单位。

统一排名层

按照任务类型筛选合格模型，合并两个接入路线的观测后计算综合得分，输出总榜和各场景专榜。模型管理页的模型列表直接按此顺序排列。

实际部署时，每条记录至少保留：

`model_id`、`task_type`、`capability_score`、`cost_per_task`、`success_rate`、`p95_latency`、`quota_headroom`、`fit_score`、`final_score`、`sample_count`、`updated_at`。

其中，`sample_count` 用来防止新上线、只有少量请求的模型凭借偶然的高成功率冲到榜首。实测数据不足时，应降低排名置信度，并结合基准分和初始评估值排序。

## 五、最终方案

采用 综合评分 + 硬性准入筛选 + 按任务类型分别排名 作为第一版方案。

默认以 Agent 编程的 `40% 能力 + 20% 费用 + 25% 可用性 + 15% 适配度` 作为总榜；同时输出能力榜、经济性榜和稳定性榜。对于代码修复、视觉分析和普通文本问答，再分别计算专榜。

最重要的一点：排名单位是模型，Zen 与 Go 作为同一模型的接入路线在排名阶段合并，不再各自占一行；需要比较渠道差异时看接入路线层的原始指标，需要切换 Go 模型时看轮转顺序。

## 六、实现对应关系

| 规格项 | 实现位置 |
| :--- | :--- |
| 评分公式与四个维度 | `internal/ranking/ranking.go` |
| 任务预设与权重 | 同文件的 `presets`（`agent-coding` / `general-text` / `vision`） |
| 路线输入构造（目录、价格、订阅分摊、运行采样） | `internal/gateway/ranking.go`；`rankingInputs` 按模型合并 Zen/Go，`rotationPlan` 仍按 Go 单路线计算 |
| 排名结果驱动轮转顺序 | `internal/gateway/rotation.go` 的 `syncRotation` + `rotation.Manager.Apply` |
| 查询接口 | `GET /api/rankings?task=`、`GET /api/rankings/tasks` |
| 可调参数 | 配置 `ranking.*`，见 `docs/configuration.md` |

接口字段与本文记录的对应：`p95_latency` 以毫秒为单位命名为 `p95_latency_ms`；`capability_score` 为 Q，`economy_score` 为 E，`availability_score` 为 A，`fit_score` 为 F，`gate` 为准入开关 G，`final_score` 为 S。未测量的维度返回空值，综合分按中性 50 分计入并同步降低 `confidence`；`sample_count` 直接来自最近 24 小时的运行采样条数。
