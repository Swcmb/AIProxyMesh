## 1. Goal

在 `D:\AIProxyMesh` 中交付整合产品：**一个具备完整 OpenCode API 网关能力、统一代理资源池、智能出口调度、自动故障切换和统一 WebUI 的单体服务**（`a.md` §1、最终建议 §386）。

四个子目标（`a.md` §1）：

1. **功能基准**：完整保留 opencode2api 的 API、协议转换、上游 Key 池、模型路由、匿名通道、配置、统计和管理能力。
2. **代理基础设施**：使用 Resin 的节点订阅、节点管理、健康检查、延迟评估、调度、熔断和恢复机制。
3. **统一管理**：一套 WebUI 管理网关、上游资源、代理节点和运行状态。
4. **精简产品边界**：删除 Resin 不再需要的独立业务模块，不无差别搬运 Resin 功能。

最终架构（双层职责划分）：

```
客户端 → opencode2api 网关（API 认证/协议转换/模型路由/Key 池/重试）
       → 统一代理调度引擎（节点池/健康度/延迟/上游成功率/冷却/429 策略）
       → 选中的出口节点 → OpenCode 实际上游（沿用原 upstream 配置地址）

WebUI（Resin 设计风格 + 全部 O2A 管理功能 + 代理节点管理）→ 统一管理 API 与状态存储
```

## 2. Purpose

- 为什么要做：两个项目各自只解决了一半问题——opencode2api 有完整的上游网关能力但没有代理资源管理；Resin 有代理池能力但业务定位不同（平台/租约/反向代理）。整合后用户只需部署、配置、管理**一个**服务（`a.md` §5.3）。
- 成功看起来是什么样：一个 `go build` 产物即可启动全部能力；所有原有 opencode2api API 与行为不变；代理出口在故障、限流、超时时自动切换且可观测；旧 `proxies`/`proxyfile` 配置升级后继续有效。
- 非目标（本规格不做）：
  - 不重新实现一个类似 opencode2api 的新网关（`a.md` §5）。
  - 不做两个项目的功能页面拼接；前端以 Resin 设计语言为基准全面重构（`a.md` §4）。
  - 不保留/不带入 §3.3 删除清单中的任何 Resin 模块。
  - 不在 v1 验收范围内追求 Tier C 协议（见 §5.3）。

| 删除项 | 具体边界 |

| 平台管理 | 不保留 Resin 的独立 Platform 业务模型及其管理页面 |

三个易混区分（`a.md` §2.3，必须遵守）：

1. 删平台隔离节点池 ≠ 删节点故障冷却：故障节点仍须暂时退出候选池。
2. 删粘性租约 ≠ 删 o2a 会话亲和性、Key 选择状态与原有代理优先绑定机制——后者按原语义保留，但不得再依赖 Resin 租约系统实现。
3. 删多接入点管理 ≠ 删 o2a 原有的 API 监听地址与独立 WebUI 管理监听地址——后者必须保留。

- 不引入 Resin 全套不需要的反向代理与租约代码（`a.md` §6 阶段 1 要求）。

## 4. Constraints

1. **交付形态**：单个 Go 可执行文件 + 单个 Docker 部署单元；React/TypeScript 前端在构建期生成静态资源并嵌入 Go 程序；运行时不需要 Node.js，不需要独立前端服务器（`a.md` §4 前端部署方式、§5.3）。
2. **禁止双进程互代**：不得用两个独立进程互相代理冒充整合（`a.md` §5.3）。
3. **上游地址唯一来源**：不新增 `target_domain`、目标域名配置或第二份 OpenCode 上游地址配置；所有上游请求从现有 `upstream.zen` / `upstream.go` / `upstream.anonymous` 读取实际目标；调度器以当前请求选择的上游 URL 确定目的地址与观测目标（`a.md` §3.1）。
4. **配置兼容**：保留 opencode2api 现有配置结构与字段语义；`proxies` / `proxyfile` 必须通过兼容层接入统一节点池，不能因升级失效（`a.md` §5.1）。
5. **配置与状态分离**：节点状态持续更新不得每次重写全部业务配置；配置更新先验证再原子切换；进行中的请求不因订阅刷新或配置重载被无故中断（`a.md` §5.2）。
6. **管理认证统一**：管理端沿用 opencode2api 的认证体系（session + CSRF）；新增代理池接口遵循 opencode2api 命名风格，不沿用 Resin 的 `/api/v1` + Bearer token 体系。
7. **管理 API 兼容**：保留 opencode2api 原有管理接口与语义，仅为订阅、节点状态、评分、冷却与切换历史补充新接口；不随意改动现有管理 API（`a.md` §4 前端部署方式末段）。
8. **界面基准**：WebUI 采用 Resin 的整体布局、导航、配色、卡片、表格、表单、状态展示与统一组件风格；不得仅换肤；功能覆盖以 opencode2api 原有管理能力为准（`a.md` §4、§396）。
9. **Go 工具链**：Resin 要求 `go 1.25.5`，本机实测 `go1.25.4 windows/amd64`。整合模块的 `go`/`toolchain` 指令必须显式处理此差异（自动 toolchain 下载或本地升级），且 CI/本地构建命令必须可复现。
10. **依赖纪律**：新依赖默认不引入；Tier B 协议依赖（`github.com/sagernet/sing`、`sing-box`、`sing-shadowsocks`、`sing-vmess` 等，具体最小集阶段 1 以 `go mod why` 裁决后回填）须先完成依赖审查（体积、许可证、跨平台构建、CGO）。Tier A（§5.3）必须零新依赖完成。
11. **许可证合规**：整合产物按 GPL-3.0-or-later 分发（opencode2api 为 GPL-3.0-or-later，属衍生组合作品）；保留 Resin 的 MIT 版权与许可证声明；随附第三方依赖清单（`a.md` §8 风险一）。
12. **仓库约定同步**：本仓库当前定位为"无源码的聚合/部署仓库"；引入整合源码后，必须按根 `AGENTS.md` 维护规则在同一次改动中更新 AGENTS.md（项目结构、构建测试命令、架构边界、开发约定）。
13. **工作区纪律**：开发在 `D:\AIProxyMesh` 新模块内进行；子模块 pin 更新（`git submodule update --remote`）与整合开发分离，不混入同一提交。

## 5. Technical Approach

### 5.1 集成形态与代码组织（核心决策）

**方案**：在本仓库新增一个顶层自包含 Go 模块（候选目录 `mesh/`，模块路径候选 `github.com/Swcmb/AIProxyMesh/mesh`；两者均为拟定，见 §12-②）。

论证：

- Go 的 `internal` 包不可跨模块导入，将 `Resin/internal/*` 作为外部依赖导入不可行（`a.md` §388 已指出）。
- 两个子模块 remote 均为上游仓库（`Resinat/Resin`、`jasonxu114514/opencode2api`），本仓库是唯一可写工作面。

```
│   └── webui/                 # 构建期嵌入的静态资源
└── webui/                     # 前端源码（Resin 设计语言，13 页）
```

### 5.2 分层职责

- **网关层**（o2a 原样）：认证、协议转换、模型路由、Key 池轮换、匿名通道、重试与响应处理。
- **调度层**（新增）：资格过滤 → 评分 → 候选选择 → 故障分类 → 冷却/熔断/恢复（两层冷却分层，§5.5）→ 尝试预算协调（单一预算池，§5.7）。
- **出口层**：节点连接到实际上游；Tier A 用标准库实现 HTTP/SOCKS5 出站与 `proxyfile` 导入。
- **管理面**：o2a 原有管理 API + 新增代理池接口；统一认证中间件。
- **前端**：Resin 设计语言的 React/TS 应用，覆盖 13 页（§5.10）。

### 5.3 出口协议 Tier 分层

| Tier | 范围 | 纳入条件 |
| :--- | :--- | :--- |
| A | HTTP / HTTPS / SOCKS5 / SOCKS5H + `proxyfile` | v1 必做，零新依赖（与 o2a 现有 scheme 集一致） |
| B | Shadowsocks / VMess / VLESS / Trojan | 不计入 v1 验收基线（条件性增强）；依赖审查通过后可提前纳入。审查项：`github.com/sagernet/sing` v0.7.18、`github.com/sagernet/sing-box` v1.12.21、`github.com/sagernet/sing-shadowsocks` v0.2.8、`github.com/sagernet/sing-shadowsocks2` v0.2.1、`github.com/sagernet/sing-vmess` v0.2.7 等包的最小必要子集（阶段 1 以 `go mod why` 裁决实际最小集）、体积、许可证、跨平台构建、CGO、版本匹配 |
| C | WireGuard / Hysteria2 / TUIC / Reality 等 | 不在 v1 验收范围；结构上预留出站接口 |

**v1 验收基线 = Tier A**（HTTP / HTTPS / SOCKS5 / SOCKS5H + `proxyfile`，零新依赖）；Tier B 纳入与否**不影响 §9 判定**。

节点**格式解析**（sing-box JSON / Clash YAML / URI）与**出站实现**分开处理：Tier 外协议节点可被解析入库并标记为 `unsupported`（可见、不入候选池），不因未实现出站而丢订阅内容。

### 5.4 调度器

评分公式（`a.md` §3.2，权重为初始参数，可配置、可用真实数据调整）：

```
S_i = 100 × (0.30·H_i + 0.15·L_i + 0.15·R_i + 0.40·U_i)

U_i = (O_i + 1) / (O_i + F_i + 2)     # 平滑上游成功率
```

| 指标 | 权重 | 计算依据 |
| :--- | :--- | :--- |
| `H_i` 节点健康度 | 30% | 连接成功率、主动探测、近期网络故障及节点健康状态 |
| `L_i` 延迟得分 | 15% | 实际上游路径延迟，优先 EWMA 平滑结果 |
| `R_i` 调度得分 | 15% | Resin 原有候选选择、负载均衡与调度策略 |
| `U_i` 上游成功率 | 40% | 经该出口访问相同上游、**可归因于出口**的成功/失败记录 |

规则：

- `H/L/R/U` 归一化到 `[0,1]`，分数越高优先级越高。
- **资格过滤先于评分**：熔断、禁用、冷却中的节点由过滤器排除，不靠低分兜底。
- **归因纪律**：只有可归因于出口的故障才影响 `U_i`；Key 额度耗尽或上游整体故障不得压低正常代理的成功率。
- **同轮不重复**：同一轮重试不得重复尝试相同节点。

### 5.5 四类故障分类（`a.md` §3.3）

| 故障类别 | 判定信号 | 处置（冷却分层见下） |
| :--- | :--- | :--- |
| 代理节点故障 | 连接拒绝、DNS 错误、连接超时、隧道建立失败 | 降低 `H_i`，切换其他节点，触发**节点层冷却** |
| Key 或模型故障 | 认证失败、额度不足、模型下架、协议不支持 | 走 o2a 现有 Key 轮换/模型回退；**不判定代理故障**，触发**o2a 通道层冷却** |
| 出口相关上游故障 | 同一上游同一 Key 在某出口失败、换出口成功 | 提高该出口失败惩罚，必要时暂时切换出口，触发**节点层冷却** |
| OpenCode 上游整体故障 | 多个不同出口出现相同上游错误 | 触发上游级退避，避免无休止遍历整个代理池，触发**o2a 通道层冷却** |

上游整体故障不得仅凭单条 5xx 认定；须结合错误类型、采样数量、不同出口结果与观测窗口。

**冷却分层（定案）**——两层冷却独立计数、独立配置、判定串联，同一失败只触发一层，禁止互相触发或延长：

| 层 | 职责范围 | 配置 | 源码依据 |
| :--- | :--- | :--- | :--- |
| 节点层冷却 | 代理节点故障、可归因于出口的上游故障（含仅某出口被限流） | `egress.cooldown`（`base_seconds` 30，`max_seconds` 900，指数退避） | 新增（移植 Resin 熔断/冷却机制） |
| o2a 通道层冷却 | Key 或模型故障、OpenCode 上游整体故障 | `FailureCooldownSeconds`（默认 15s，o2a 既有语义） | `config.go:100/143`、`gateway.go:74` |

判定串联顺序：请求失败 → 归因分类（本节四类）→ 出口相关 → 节点层；否则 → 通道层。同一失败事件只更新一层的计数与冷却时间。

### 5.6 HTTP 状态与 429 / Retry-After 策略（`a.md` §3.4）

| 情况 | 默认处理原则 |
| :--- | :--- |
| 连接层故障 | 排除已失败节点，选择其他合格节点 |
| HTTP 429 | 按状态码、请求方法与出口切换策略判断是否换出口；遵循 `Retry-After` |
| HTTP 401 / 403 | 优先执行原 Key 认证与轮换机制，不默认惩罚正常代理 |
| HTTP 5xx | 按可配置规则决定重试或换出口，同时判断是否为上游整体故障 |
| 不可重试的 4xx | 保留 o2a 当前路由的错误语义，不盲目轮换整个代理池 |
| 客户端取消 | 不得误判为代理故障或触发不必要的重试 |

429 细则：

- 解析 `Retry-After` 的秒数或 HTTP 日期；仅当剩余请求时限足以容纳等待与重试才继续；超过时限则停止重试并返回相应错误（不得忽略服务器等待要求）。
- 归因三分（衔接 §5.5 冷却分层）：仅某出口被限流 → 提高该出口失败惩罚并触发**节点层冷却**；同 Key 多出口均被限流 → 考虑 Key 额度/账号级限制，触发**通道层冷却**（不冷却节点）；多出口对整上游同错 → 考虑上游整体状态，触发**通道层冷却**。
- 状态码与请求方法策略可配置；**目标域名不单独配置**，策略始终作用于 o2a 上游调用链路。

### 5.7 统一重试预算：单一预算池（`a.md` §3.5 的优化变体；不采纳其独立节点尝试预算建议，留痕见附录 A Round 1）

- **唯一总预算** = o2a 既有 `retry.max_attempts`（默认 3；定义 `config.go:64/141`；消费点 `upstream.go:689`、`refresh.go:246`）。**不新增独立节点尝试预算**（原草案 `node_attempt_budget` 已删除）：切换出口节点消耗一次尝试，最坏总上游尝试次数 = `retry.max_attempts` = 3，不存在叠加放大。
- 每次请求共享：总体请求超时、每次上游尝试超时、已尝试节点集合、按错误类别的重试资格、SSE 首个有效输出前后的重试边界。
- 请求体仅在可安全重放时才允许下一次尝试。
- 流式响应：一旦向客户端发出有效输出，不得重放上游或拼接第二份回答；继续遵循 o2a 现有流式中断与错误处理行为。

- 上游故障判断：不把上游整体错误误判为所有节点故障。
- 429 策略：满足配置策略时更换出口，且正确遵循 `Retry-After`（归因三分衔接冷却分层，§5.6）。
- 冷却分层：节点故障/可归因出口故障仅触节点层冷却（`egress.cooldown`，30–900s）；Key/模型故障与上游整体故障仅触 o2a 通道层冷却（`FailureCooldownSeconds`，15s）；同一失败不双触发、两层不互相触发或延长（§5.5）。
- 尝试预算池：任一请求的最坏上游尝试次数 ≤ `retry.max_attempts`（默认 3）；换节点消耗一次尝试，无 3×3 叠加放大（§5.7）。
- 流式响应安全：首个有效输出前后遵循原重试与错误处理语义，不拼接两份回答。
- 配置热重载、持久化、异常恢复及升级回滚。
- WebUI：所有原有业务操作均有对应页面，统一 Resin 风格。

证据形式：命令输出、测试报告、日志片段、UI 截图（截图仅作辅助，不作唯一证据）。

## 8. Iteration Strategy

- 外层控制器为 SPAC-plus-auto：负责审批门、执行模式判定（Direct 或 /goal）与最终验收；`/goal` 仅按本规格驱动迭代，不与外层控制器争夺控制权（审批、验收、回滚决策归外层）。
- 顺序：阶段 0→7 串行推进；每阶段内部进一步拆分小提交。
- 每轮循环：改动 → `go build ./...` → 相关测试 → 全量测试（阶段末）→ `go vet ./...` → git 提交（提交信息说明阶段与范围）。
- 修复循环上限：同一问题连续 3 次修复未果 → 触发回滚评估（回滚到最近稳定提交），并作为阻塞点上报告。
- 评审循环（本规格自身）：document-reviewer 子代理评审 ≤3 轮；未共识时向用户呈现当前最佳版本 + 未决问题清单。
- 回滚：代码用 `git revert`/`git reset --hard <最近稳定提交>`；配置用上一版本文件；状态库保留备份（阶段 1 确定备份策略）。

## 10. Contingency

| 触发 | 应对 |
| :--- | :--- |
| 许可证合规无法达成（GPL 义务与 MIT 声明冲突处理失败） | 停止发布；重新评估分发形态（如分离进程分发）并回报用户——发布阻塞项 |
| 存在用户维护的 opencode2api 定制分支（§12-① 为真） | 阶段 0 重新以该分支为目标基线做全量盘点，重跑受影响的后续阶段 |
| 本机/CI Go 版本 < 1.25.5 且 `GOTOOLCHAIN=auto` 下载不可用（离线/受限网络） | 离线安装 Go ≥ 1.25.5 后在 `go.mod` 固定 `toolchain go1.25.5`；必要时显式 `GOTOOLCHAIN=local` 禁止自动下载；验证离线环境 `go build ./...` 可复现并记录证据 |
| Tier B 依赖审查不通过 | v1 仅交付 Tier A；Tier B 延后为独立迭代项；Tier 外节点保持 `unsupported` 可见状态 |
| 跨平台构建失败（某目标平台） | 缩减目标矩阵（经用户确认）或逐平台修复；Windows 主开发平台优先保通 |
| 状态存储受阻：SQLite（已定案，§5.9）跨平台构建失败或迁移机制不可行 | 按 §5.9 回退条款回退 JSON/JSONL 状态文件；接口不变、仅替换实现；阶段 1 记录决策与理由，回归中复验 §9-10 |
| 上游整体故障场景下退避被误触发/漏触发 | 收紧判定门槛（多出口共识 + 采样窗口），增加回归用例；必要时给出手动覆盖开关 |
| SSE 已输出后的失败处理与预期不符 | 以 o2a 现有行为为唯一基准，不做行为增强；补测试固定语义 |
| 新前端工作量超预期 | 按 13 页清单优先级分批交付（代理页面优先），但 §9-11 验收不得降级 |
| 测试基础设施缺失（某层无测试可跑） | 阶段 0/1 补测试骨架；缺失层以端到端用例兜底，并在报告中标注覆盖缺口 |

## 11. Blocking / Stop Conditions

出现以下任一情况：**停止当前迭代，回滚到最近稳定状态，向用户报告（使用 /goal 时附迭代摘要、验证结果、未决问题、回滚状态）**。

1. 阶段 3 / 5 / 6 的核心验收项失败，且同一问题 3 次修复未果。
2. 许可证合规无法达成（GPL 义务无法履行或 MIT 声明无法保留）。
3. 依赖冲突导致 Tier A 路径（HTTP/SOCKS5 + `proxyfile`）也无法构建或运行。
4. 出现无法修复的 opencode2api API 兼容性破坏（路径/认证/响应语义不兼容）。
5. §12 中标注为"阻塞性"的未决问题未获用户答复而无法安全继续。
6. 用户给出 REJECT，或在 REVISE 后未获新审批。
7. 发现需要修改子模块仓库才能继续（违反 §3.4 只读边界）——改走本仓库模块内方案或报告用户。
