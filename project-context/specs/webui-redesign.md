# AIProxyMesh Web UI 全面升级提示词

## 一、项目背景

目标项目：

- GitHub 仓库：https://github.com/Swcmb/AIProxyMesh
- OpenCode 官方仓库：https://github.com/anomalyco/opencode
- OpenCode Web 前端：https://github.com/anomalyco/opencode/tree/dev/packages/app
- AWS Cloudscape 官方组件库：https://github.com/cloudscape-design/components
- Vercel Geist 官方仓库：https://github.com/vercel/geist

请直接检查当前工作区中的 AIProxyMesh 项目，并基于现有代码完成 Web UI 的全面设计升级与工程实现。

**核心目标：将 AIProxyMesh 打造成具有 OpenCode 风格的现代 AI 开发者基础设施管理平台。**

这不是重新开发一个新项目，也不是只制作一个静态原型。必须在完整保留现有业务能力、后端 API、代理逻辑、配置格式和兼容性的前提下，完成真实可用的前端升级。

---

## 二、设计参考与官方资料

必须优先研究以下官方开源项目。先检查其真实代码、组件实现、样式规范和许可证，再决定采用何种方式借鉴或集成。

### 1. OpenCode：主要产品体验与视觉参考

官方仓库：https://github.com/anomalyco/opencode

Web 前端目录：https://github.com/anomalyco/opencode/tree/dev/packages/app

重点借鉴：

- 深色主题与开发者工具的整体气质。
- 紧凑、清晰的侧边栏和导航结构。
- 页面层级、排版、间距和细边框。
- 列表、状态、操作按钮与内容区域的组织方式。
- 设置页面的信息分组。
- 加载、空状态、错误提示和交互反馈。
- 适合长时间使用的界面密度和视觉一致性。

要求：

- 以实际源码为依据，不要凭印象仿制。
- 优先复用适合当前技术栈的设计思路与组件模式。
- 不要将 OpenCode 中与 AIProxyMesh 无关的会话、对话或编程功能搬入项目。
- 不要为了模仿外观而引入不必要的框架迁移。
- 不要直接复制与项目不兼容的内部实现。
- 如需引入其代码或资源，先核实当前许可证和相关依赖要求。

### 2. AWS Cloudscape：后台管理交互参考

官方仓库：https://github.com/cloudscape-design/components

重点借鉴：

- 数据表格、排序、分页和筛选。
- 多条件搜索。
- 资源状态和健康状态展示。
- 详情面板、抽屉和上下文操作。
- 配置表单、校验和错误反馈。
- 批量操作、确认弹窗和危险操作提示。
- 加载、空数据、无搜索结果等状态。
- 面向复杂管理任务的信息架构。

Cloudscape 主要用于帮助完善复杂后台交互，不要求为了使用它而替换整个现有前端技术栈。

如果项目使用的框架与 Cloudscape 不兼容，或者集成成本过高，则参考其交互规范，在现有技术栈内实现相应能力。

### 3. Vercel Geist：视觉规范参考

官方仓库：https://github.com/vercel/geist

重点借鉴：

- 字体层级和文字可读性。
- 简洁的布局和合理留白。
- 细边框、低干扰分隔线。
- 深色背景与中性色体系。
- 按钮、输入框、下拉菜单和标签的统一规范。
- 一致的圆角、尺寸、间距和交互状态。
- 现代开发者产品的精致感。

注意：Geist 是视觉与设计资源参考，不应被误认为一套可以直接覆盖所有后台业务需求的完整管理系统。

### 4. 设计优先级

发生设计冲突时，按以下优先级执行：

1. AIProxyMesh 现有业务功能、兼容性和正确性。
2. OpenCode 的整体产品体验和开发者工具风格。
3. Cloudscape 的复杂后台交互模式。
4. Geist 的视觉规范和细节。
5. 当前项目的技术栈、性能、可维护性和无障碍要求。

最终效果应当是统一设计，而不是把三个项目的页面拼在一起。

## 三、各页面设计要求

### 1. 总览仪表盘

以 OpenCode 的开发者产品风格为主。

要求：

- 采用简洁、紧凑、信息密度合理的布局。
- 清晰展示项目现有的核心运行状态。
- 在后端已经提供相应数据的前提下，展示代理运行状态、供应商或节点健康情况、请求量、错误率、延迟、限流情况等指标。
- 核心指标应具备明确的标签、单位和合理的时间范围。
- 使用统一的状态标签、简洁的图表和信息卡片。
- 对异常、离线、错误和警告状态提供清晰提示。
- 如果后端没有提供某项指标，不得编造数据；应隐藏该指标，或明确展示为不可用。
- 不要为了追求仪表盘效果而增加大量无实际意义的图表。
- 首屏应优先呈现最重要的运行状态和需要处理的问题。

### 2. 模型与代理节点管理

以 OpenCode 的紧凑列表风格为主，结合 Cloudscape 的管理交互。

要求：

- 复用现有模型、供应商、代理节点和路由数据结构。
- 根据当前后端能力展示名称、类型、状态、模型、优先级、健康信息等字段。
- 支持现有功能范围内的搜索、筛选、排序和分页。
- 提供清晰的查看、编辑、启用、禁用、测试或删除操作；仅实现后端实际支持的操作。
- 对不同状态使用一致的标签和图标。
- 复杂详情可采用抽屉、侧面板或独立详情页。
- 支持加载、空数据、错误和无搜索结果状态。
- 对危险操作显示确认提示。
- 不得仅在前端修改状态却不向后端提交。
- 不得用模拟节点、假健康状态或虚构的延迟数据替代真实数据。

### 3. 请求日志与调用详情

以 Cloudscape 的表格、筛选和详情面板为主要参考。

要求：

- 保留现有请求日志及查询能力。
- 使用适合高密度数据的表格布局。
- 根据实际数据提供时间、状态码、模型、供应商、耗时、错误信息等字段。
- 支持现有 API 能力范围内的排序、筛选、分页和搜索。
- 通过详情面板或详情页查看单次请求的完整信息。
- 如后端记录了相关信息，可展示请求 ID、上游信息、重试情况、错误原因和耗时分解。
- 明确区分成功、失败、超时和其他状态。
- 大数据量场景优先使用后端分页与筛选，避免一次性加载全部日志。
- 不得在普通列表中无必要地暴露完整密钥、Authorization 请求头或其他敏感信息。
- 对日志为空、加载失败和无匹配结果提供明确反馈。

### 4. API Key 与供应商配置

以 Geist 的简洁表单风格为主，借鉴 Cloudscape 的表单交互。

要求：

- 先审计项目当前的配置方式、配置文件格式、后端接口和密钥管理方式。
- 使用统一的表单布局、字段间距、标签、帮助说明和校验提示。
- 按供应商或配置类别合理组织表单。
- 正确处理必填项、可选项、默认值和字段依赖。
- 保留现有密钥配置、供应商配置和模型映射能力。
- 密钥默认脱敏；仅在业务确实需要且现有安全设计允许时提供查看或复制功能。
- 不得将密钥写入前端源码、控制台日志、URL、分析事件或不必要的浏览器持久化存储。
- 不得擅自改变现有配置格式或破坏旧配置兼容性。
- 对保存成功、保存失败、字段无效和连接测试失败提供清晰反馈。
- 如果后端支持测试连接、验证配置或探测供应商，应接入真实接口。
- 保存配置前后必须正确处理数据刷新、错误恢复和未保存变更提醒。

### 5. 系统设置

以 OpenCode 的侧边栏和设置页面为主要参考，使用 Geist 的视觉规范。

要求：

- 按照功能类别组织设置项。
- 保持统一的页面宽度、表单宽度、间距和标题层级。
- 使用清晰的设置分组、说明文字和操作反馈。
- 保留现有所有设置项，不得因为页面重构而遗漏。
- 对有风险的设置修改增加必要的确认和说明。
- 对无法修改或只读的设置明确显示其状态。
- 如设置涉及服务重启、配置重载或其他后端动作，必须遵循现有 API 语义，不得假设保存即生效。
- 设置变更后，应根据实际后端能力刷新页面状态。

### 6. 全局布局与通用组件

统一以下内容：

- 侧边栏和主内容区。
- 页面标题与操作区域。
- 按钮、输入框、选择器、开关和表格。
- 状态标签、提示信息和确认弹窗。
- 加载指示器、骨架屏、空状态和错误状态。
- Toast 或现有通知机制。
- 抽屉、详情面板和弹窗。
- 深色与浅色主题（仅在现有技术栈和工作量合理的情况下完善）。
- 键盘操作、焦点状态和基础无障碍支持。

要求建立统一的设计 Token，集中管理颜色、间距、字体、圆角、边框、层级和过渡效果。

不要在各个页面里重复定义互相冲突的颜色、尺寸和样式。

## 四、功能完整性是硬性要求

**禁止为了视觉升级删减、简化或替换 AIProxyMesh 已有功能。**

实施前必须审计：

- 当前全部路由和页面。
- 所有前端组件和页面入口。
- 所有后端 API 的调用位置。
- 所有表单、按钮、菜单和交互操作。
- 所有配置项及其读写流程。
- 登录、认证、权限和会话机制（如果存在）。
- 模型、供应商、代理节点和路由相关功能。
- 日志、监控、健康检查和错误处理。
- 现有测试、构建命令和部署方式。

必须建立旧功能到新页面的映射清单。

如果某个功能没有明显的页面归属，应在重构前明确其保留位置，而不是直接删除。

如果某项能力目前只有后端接口、没有现成 UI，也不能据此擅自将其视为废弃功能。

除非发现明确的安全问题或严重缺陷，否则不要修改与 UI 无关的核心代理转发、认证、重试、路由和配置语义。

若确实必须修改后端接口，应先说明原因，并同步维护调用方、测试和兼容性。

## 五、技术实现要求

### 阶段 0：环境与项目审计

先检查当前工作区，不要直接开始覆盖代码。

至少完成：

1. 确认实际仓库、分支和工作区状态。
2. 检查 `git status`，识别用户未提交的修改。
3. 阅读项目 README、开发文档、依赖清单和运行说明。
4. 确认前端框架、版本、构建工具、样式方案和路由方案。
5. 确认后端框架、API 结构和数据模型。
6. 运行现有测试或基线构建，记录已有失败。
7. 整理当前页面和功能清单。
8. 识别可复用的组件、设计 Token 和现有 API 客户端。

输出审计报告，记录关键文件、技术栈、风险和实施计划。

不得覆盖用户修改，不得泄露 `.env`、密钥、Token 或其他敏感内容。

### 阶段 1：制定设计与迁移方案

基于审计结果制定：

- 页面信息架构。
- 页面与旧功能的映射表。
- 全局布局方案。
- 设计 Token。
- 通用组件清单。
- 各页面交互方案。
- 依赖调整计划。
- 兼容性与回滚方案。

在现有技术栈可以合理实现的情况下，优先保留原有框架和依赖。

不要仅为了引入某个设计系统就迁移整个项目。

如果需要新增依赖，先确认其维护情况、许可证、版本兼容性和体积成本。

### 阶段 2：实施 UI 重构

按以下顺序执行：

1. 建立全局设计 Token 与主题。
2. 建立统一的应用布局、侧边栏和导航。
3. 实现通用表单、状态标签、通知和确认组件。
4. 重构总览仪表盘。
5. 重构模型与代理节点管理。
6. 重构请求日志与调用详情。
7. 重构 API Key 与供应商配置。
8. 重构系统设置。
9. 迁移其他审计发现的页面和功能。
10. 清理重复样式、失效组件和不再使用的代码。

每完成一个模块，都要验证其数据绑定、交互和原有功能，不要一次性重写所有文件后才开始测试。

### 阶段 3：功能与视觉验证

至少完成：

- 项目原有测试。
- 前端构建和类型检查（如项目支持）。
- 关键页面加载验证。
- 路由和导航验证。
- 所有主要表单的读写验证。
- API 请求成功和失败时的行为验证。
- 加载、空状态和错误状态验证。
- 关键表格的筛选、排序、分页验证（如适用）。
- 危险操作确认流程验证。
- 深色主题下的可读性检查。
- 常见桌面分辨率与较窄窗口的布局检查。
- 控制台错误与无效网络请求检查。
- 对敏感数据的脱敏检查。

如果具备浏览器自动化工具，应实际打开运行中的项目进行视觉和交互验证，而不只是检查源码。

不得将“页面能够编译”视为全部工作已经完成。

### 阶段 4：回归与交付

最终检查：

- 旧功能是否全部保留。
- API 请求格式和配置格式是否兼容。
- 是否引入未经允许的后端语义变更。
- 是否有未使用依赖、无效样式和重复实现。
- 是否存在硬编码假数据。
- 是否存在密钥泄露风险。
- 构建、测试和运行命令是否可用。
- README 或相关文档是否需要更新。

输出最终交付报告。

## 六、明确禁止事项

1. 不得只输出设计建议、计划或代码片段，必须在当前工作区实际实施。
2. 不得只做静态 HTML、截图或不可交互的演示页面。
3. 不得使用假数据伪装真实运行状态。
4. 不得删除旧页面、按钮、API 或配置项来简化重构。
5. 不得擅自替换后端、认证系统、数据库或核心代理实现。
6. 不得随意迁移前端框架。
7. 不得引入不必要的重量级依赖。
8. 不得把三个参考项目的组件直接拼成风格不一致的界面。
9. 不得覆盖用户已有修改、提交代码或推送远程仓库，除非用户明确授权。
10. 不得在没有实际执行的情况下声称测试通过。
11. 不得因某项功能实现困难而静默跳过；必须记录原因、影响和后续方案。
12. 不得在报告、截图、日志或提交记录中暴露敏感凭据。

只有同时满足以下条件，才算完成：

- [ ] 已完成现有代码与功能审计。
- [ ] 已建立旧功能到新 UI 的映射清单。
- [ ] 已实现统一的 OpenCode 风格全局布局。
- [ ] 已统一 Geist 风格的视觉规范。
- [ ] 复杂管理交互参考 Cloudscape 的设计模式。
- [ ] 五类核心页面已完成真实实现。
- [ ] 审计发现的其他旧页面和功能均得到保留。
- [ ] 所有主要按钮和表单均连接真实业务逻辑。
- [ ] 没有以假数据替代真实后端数据。
- [ ] 现有 API、代理逻辑和配置兼容性未被无故破坏。
- [ ] 构建、测试和关键交互验证均已执行并如实报告。
- [ ] 文档已更新，交付报告包含实际修改文件、测试结果和未解决问题。

## 八、最终报告格式

完成后按以下格式汇报：

### 1. 实施结果
概述完成的 UI 升级及其主要改进。

### 2. 页面改造清单
列出每个页面的改动、对应文件和保留的旧功能。

### 3. 通用组件与设计规范
列出新建或复用的布局、表格、表单、状态标签、主题与设计 Token。

### 4. 功能完整性
说明如何验证原有功能、API 调用、配置读写和关键操作。

### 5. 测试结果
逐项列出实际执行的命令、结果、失败项及其原因。未执行的测试明确标记为未执行。

### 6. 文件变更
列出主要新增、修改和删除的文件。任何删除都必须说明原因。

### 7. 剩余问题
列出未完成项、已知缺陷、兼容性风险和建议后续步骤。

### 8. 启动与预览
提供经过仓库实际验证的启动命令和访问地址；如果无法启动，明确说明阻塞原因。

现在开始执行阶段 0。审计完成后继续推进后续阶段，不要只停留在方案设计。遇到可能破坏用户数据、覆盖现有修改或需要不可逆操作的情况，先暂停并请求确认；其余问题优先依据代码和测试结果自行判断并实施。
