## 关键发现

1. **选路 p99 处于边界**：86k 节点、4 键时多次运行在 4.88–6.12ms，稳定达标需要继续降低评分/索引开销或降低 `route_sample_size`；本次不宣称 10 万节点达标。
2. **4 键内存超预算**：按规格默认 `max_keys_per_node=4`，86k×4 的健康表+索引增量约 540–570MB，超过 200MB/30MB 分项与 300MB 进程增量。规格给出的补救是降低 `max_keys_per_node`；实测 1 键时进程增量 240MB，满足 300MB 上限。大规模池建议 `max_keys_per_node=1` 或后续压缩 `KeyStats`（时间字段改 int64、缩小表/索引结构）。
3. **公平性修复有效**：原实现按 `pool.List()` 的 map 随机顺序推进游标，且高优先级状态会挤占低优先级键；改为按节点 ID 排序的稳定环 + 未入堆键无条件首次入堆后，300 轮覆盖 100%。堆满淘汰由 O(n) 改为双堆 O(log n)。
4. **全量刷新可用**：81k 公共代理 5 分钟完成两阶段刷新，RSS 增量 268MB；HTTP 可达仅 65 个，证明免费池需要真实流量/金丝雀持续积累证据，符合规格假设。
5. **关闭保存**：基准进程在 10s 关闭保存窗口内未写完 8 万节点快照，已把关闭保存上限调整为 60s；后续需在真实部署复核保存耗时。

## 复现

```bash

  -run TestBench86kLive -v -timeout 120m

# 仅内存（1 键）
MESH_LIVE_PRESETS=1 MESH_BENCH_KEYS=1 MESH_BENCH_MEMORY_ONLY=1 \
  go test -tags live ./internal/egress -run TestBench86kLive -v -timeout 30m

# 全量快速刷新
MESH_LIVE_PRESETS=1 MESH_LIVE_FULL_REFRESH=1 go test -tags live ./internal/egress \
  -run TestFullRefresh86kLive -v -timeout 120m
```

## 结论

- 选路 p99 在 86k 真实池上接近但未稳定达到 5ms；公平性达到 100%。
- 4 键内存不满足规格预算，需降低 `max_keys_per_node` 或压缩结构；1 键满足进程 300MB 上限。
- 81k 全量刷新与真实可达率已实测；公共代理质量与规格假设一致。
